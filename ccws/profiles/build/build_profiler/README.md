Build profiling
===============

This profile instruments the compilation to analyze compilation time of the
packages in the workspace. It is based on `ClangBuildAnalyzer`
<https://github.com/aras-p/ClangBuildAnalyzer>, which reports the slowest
compilation units, instantiations of expensive templates, and the most
expensive headers using the JSON timeline files generated by the
`-ftime-trace` feature of `clang`. The timeline files are also merged into a
single trace which can be opened in interactive HTML viewers.

Reports are stored in `artifacts/build_profiler/`.

Design
------

- The profile is **compiler dependent**: `-ftime-trace` is a Clang feature,
  so `clang` is used regardless of anything else and this profile **cannot be
  used as a mixin** over other build profiles.
- Compilation caches are disabled since cached compilations are not executed
  and distort the measurements:
  - `ccache` and `buildcache` are disabled via `CCACHE_DISABLE` and
    `BUILDCACHE_DISABLE` in `setup.bash`;
  - compiler launchers configured by the workspace extras are overridden
    with an empty launcher in `toolchain_body.cmake`.
- `-ftime-trace` is added to the compilation flags; `clang` generates one
  JSON timeline file next to every object file.
- `CMAKE_BUILD_TYPE` is forced to `RelWithDebInfo` to match the default CCWS
  build profile (`reldebug`).
- Tools are **never built** in this profile, only downloaded. Prebuilt
  `ClangBuildAnalyzer` binaries exist for x86_64 only; on other platforms the
  installation is skipped with a warning and the binary has to be installed
  manually (e.g. `cmake` builds of
  <https://github.com/aras-p/ClangBuildAnalyzer> work unchanged).
- `compile-time-perf` <https://github.com/jrmadsen/compile-time-perf> was
  evaluated and rejected: it provides no prebuilt binaries, which cannot be
  reconciled with the downloads-only policy above, while its measurements
  (per command wall clock time, CPU time, peak memory usage) largely overlap
  with what `-ftime-trace` provides.

Usage
-----

- Install the tools:
  `make bp_install_build BUILD_PROFILE=build_profiler` (`clang` and
  `ClangBuildAnalyzer`).
- Build and analyze: `make <pkg> BUILD_PROFILE=build_profiler`; the analysis
  is also executed after every build.
- Regenerate the reports without recompilation:
  `make bp_build_profiler_analyze BUILD_PROFILE=build_profiler`.

Reports
-------

- `artifacts/build_profiler/clang_build_analyzer.txt` -- text report of
  `ClangBuildAnalyzer`.
- `artifacts/build_profiler/time_traces.json` -- all time traces of the
  build directory merged into a single trace (one track per compilation
  unit) by `ccws_merge_time_traces.py`.

HTML reports
------------

`ClangBuildAnalyzer` cannot generate HTML reports, and no maintained
alternative tool can (see below). However, Clang time traces use the Chrome
Trace Event format, so the merged `time_traces.json` can be opened in fully
interactive HTML viewers:

- <https://www.speedscope.app> (flamecharts, also available as an offline
  self-contained download);
- <https://ui.perfetto.dev>;
- `chrome://tracing` in Chromium-based browsers.

Alternative tools
-----------------

- `CompileScore` <https://github.com/Viladoman/CompileScore> (active):
  aggregates `-ftime-trace` files into a compact score file using a
  downloadable extractor; visualization happens in a Visual Studio extension
  or a standalone GUI application, which does not fit a Linux CI setup.
- `SeeProfiler` <https://github.com/Viladoman/SeeProfiler>: Electron GUI
  application which aggregates and visualizes time traces, no report files
  are generated.
- `crofiler` <https://github.com/HadrienG2/crofiler>: terminal UI over
  `-ftime-trace` data, archived and unmaintained.
- `time-trace` <https://github.com/romanpauk/time-trace>: converts time
  traces to `perf.data` for analysis with Linux perf tooling.

`ClangBuildAnalyzer` remains the best fit for text reports in CI, which is
why this profile is based on it.

Limitations
-----------

- Only `clang` is supported, see above.
- `ClangBuildAnalyzer --all` and the trace merger scan the whole build
  directory, so the reports include the traces of all the packages built
  there with this profile, not only the ones specified by the last
  `PKG=...`.
